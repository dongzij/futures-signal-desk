## 一、合约栏：主力连续 + 3 个主力合约（共 4 个按钮）

### 1.1 旧口径错在哪

旧 `probe_contracts()` 把「最近 2 个月 ~ 未来 8 个月」**全部 12 个月**都探测一遍，
只要有 40 根日线就收录。玻璃因此打包了 12 个按钮：FG2609/2610/2611/2612/2701…2708。
其中 2610/2611/2612/2702/2703/2704/2706/2707/2708 **永远成不了主力**，纯属噪音，
还白占 7 份分钟数据（dist/data 曾达 7.4 MB）。

另一个连带 bug：`KEEP_MIN = 40` 把刚挂牌的远月直接踢掉。
FG2709 当时只有 **37 根**日线，于是「有真实持仓量、有真实成交」的 2709 反而显示不出来。

### 1.2 新口径（`data_build.probe_main_contracts`）

| 规则 | 实现 |
|---|---|
| 认哪些月份 | 复用 `build.MONTHS` 这一既有真源：FG/MA/M/Y/P/SM = **1/5/9**，HC = **1/5/10**。非主力月份不进栏，也不打包 |
| 谁是当前主力 | 尚未进入交割月、**持仓量最大**的合约——与 `panama_adjust` 判主力的口径完全一致 |
| 后两个怎么取 | 沿同一周期往后走，只收「已挂牌且有真实持仓量」的；未挂牌自然跳过，等它挂牌自动补位 |
| 数量 | `MEMBER_AHEAD = 2` 锁死为 3 个合约 + 主力连续 = 4 个按钮。远月挂牌再多也不会变长 |
| 怎么轮动 | 每次构建重算。旧合约进交割月 → `_ct_ym(cid) > 当月` 自动失效让位；新远月挂牌 → 自动进栏。**无需人工维护** |
| 入选门槛 | `MEMBER_MIN = 20`（够画 MA20 即可），不再用 40 误杀新合约 |
| 分钟数据 | 只给这 4 个合约（原来 6 个），体积同步下降 |

验收口径：按钮数 = 1（主力连续）+ len(contracts)，且 `contracts[0].front == True`。

### 1.3 数量锁定：永远是 4 个按钮

`MEMBER_AHEAD = 2` 把栏位锁死为「当前主力 + 后两个 = 3 个合约」，加上主力连续正好 **4 个按钮**。
这一点很关键：如果不锁，2027 年 1 月 2801 挂牌后会自动变成 5 个、6 个，越堆越多，
又退回"把所有已挂远月都摆出来"的老路。

这是**滚动窗口**，不是"把能凑的都摆出来"：

```
2026-11   FG2701 / FG2705 / FG2709
2027-02   FG2705 / FG2709 / FG2801     ← 2701 进交割月自动让位，2801 自动补位
2027-06   FG2709 / FG2801 / FG2805
```

用户举的例子「2027-02-01 移除 2701 补 2805」正是这个滚动窗口的自然结果
（那时序列是 2705/2709/2801/2805，只取前 3 个）。

> 顺带核实：2026-11-12 玻璃 2801 在新浪报价为空（`var hq_str_nf_FG2801="";`），
> 说明确实还没挂牌 —— 但这不影响按钮数，锁的是位置不是挂牌情况。

### 2.2 新增 `ops_alert.py`

| 触发点 | 时机 | 行为 |
|---|---|---|
| `--job-failed` | `daily.yml` 任一环节失败（`if: failure()`） | **立即**推微信，附失败原因 + 当前产物状态 + Actions 链接 |
| `--final` | 北京 20:20 之后，由外部定时器 20:30 触发 | 达标**静默**；built 没刷新 / 7 品种末根不齐 → 推一条告警 |

要点：

- 20:30 已过 20:00 禁写时段，这一班**只终检不写盘**，不会污染日线；
- 终检只认外部定时器（`client_payload.mode == "final"`），GitHub schedule 的迟到班次不推送，
  避免一天重复几次打扰；
- 告警是运维类，**不受** `post_push` 的 15:00–20:00 静音闸门约束——那个闸门是防半夜收到信号，
  不是让故障也静默；
- 通道缺失时日志明写「未通知」，绝不伪造已发送；
- `ALERT_DRY=1` 可本地演练不真发。

## 三、顺带修掉的两个真 Bug

### 3.1 engine.py `_pivot` 越界（当天 #35/#36 崩溃的根因）

`_pivot(bars, 0, 30)` 在数组末端会让 `hi` 等于 `len(bars)`，取 `bars[k+j]` 越界。
修法：`for k in range(min(hi, len(bars)-1) - 1, max(lo+w, w), -1)`，数组末端不判 pivot。
回归证明：33,320 处比对，18 处差异**正好是旧版抛 IndexError 的那几处**，其余逐位相同，
信号逻辑零改动。

### 3.2 「提交更新」裸 git push 会被顶掉

构建要跑十几分钟，期间只要有人推了代码，`git push` 就报
`! [rejected] main -> main (fetch first)`——2026-11-12 20:09 那班就是这样白跑的：
数据全对、校验全过，只差最后一步没推上去。

修法：push 前 `git pull --rebase --autostash`，失败退避 10 秒重试 3 轮，仍失败才报错退出。
