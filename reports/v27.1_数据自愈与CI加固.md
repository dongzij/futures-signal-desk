## 四、自愈机制（三层，覆盖三类故障）

### L0 取数层 · `build.py`
- `http_get` 单次超时 25s → 20s，重试 2 次 → **4 次指数退避**（0.8 / 1.6 / 3.2 / 6 秒）：快速失败 + 多次重试，比死等一次更适合国内网络。
- 新增 `FRESH_BYPASS=1`：`cache_load` 直接返回 None。否则 `fetch_daily` 的 4 小时缓存会把「昨天的 K 线」当成「今天已取到数」，自愈重试永远发现不了问题。

### L1 job 内 · `fresh_guard.py`（`daily.yml` 两个新步骤）
- **写盘前 `python fresh_guard.py`（只读预检）**：绕过缓存逐个探测 7 个主力连续日线末根；要求 7/7 都 ≥ 期望交易日。未到位就 **等 240 秒重取，最多 5 轮**（用户要求的 3–5 分钟粒度）。
- 为什么不把 `daily.py` / `data_build.py` 放进重试循环：它们会写 `state.json`、推微信、清空重建 `dist/data`，重复执行会重复写账本、重复推消息。所以先把「取数」反复做到位，正式流程只跑一次。
- **降级分支**：5 轮后仍无当日新 bar、但 7/7 末根彼此一致 → 判定休市或数据源未出新数，打 `::warning::` 并放行（复用旧数据，不产生假 bar）。只要品种缺失或末根不一致，一律 `exit 1` 阻断写盘。
- **渲染后 `python fresh_guard.py --verify`**：校验 7 品种末根一致、`data/` 与 `dist/data/` 逐字节一致、`index.html` 与 `dist/index.html` 一致、页面含 v27 铁律文案、`index.built` 是今天、`extGate.enabled=true`。任一不通过就阻断「提交更新」，由 watchdog 下一轮补跑。
- `timeout-minutes` 30 → 45，容纳 5 轮 × 4 分钟重试。

### L2 job 外 · `guard.yml` + `guard_watch.py`
- 7 个只读巡检班次（北京 15:55 / 16:20 / 16:45 / 17:10 / 17:40 / 18:10 / 18:40），最晚 18:40，距 20:00 闸门留 80 分钟。
- 读线上 `data/index.json` 的 `built` 与 7 品种末根（带 4 次重试），若 `built` 未刷新到今日 15:20 之后、或 7 品种不齐/不一致 → 通过 GitHub API 派发 `daily.yml` 补跑。
- 防重复：已有 `in_progress`/`queued` 的 `daily-scan` 时跳过；`built` 距今 < 12 分钟跳过；每轮最多派发一次。
- `permissions: contents: read, actions: write`；最后有 `git status --porcelain` 零改动断言。

### 纪律边界（关键）
- `fresh_guard.py` 只在北京 **15:00–20:00** 工作，重试按「起始时刻 + 累计轮次 × 240s」推算，**一旦会跨过 20:00 立即停止**。
- `guard_watch.py` 在 ≥20:00 时**硬断言不触发**任何补跑，只打 warning。
- 因此补跑拉到的永远是日盘完整日线；21:00 后的夜盘半截 bar 属于下一交易日，绝不会写进 `state.json` / `data/`。
- **cron 仍是 15:20 / 15:50 两班，没有新增写盘班次**；watchdog 派发的是同一套 `daily.yml` 正式流程，并同样经过 `fresh_guard` 预检与 `nightgate` 闸门。
- K 线、信号、出场账本、6 条推送通道、v27 极值禁令一律未动。
