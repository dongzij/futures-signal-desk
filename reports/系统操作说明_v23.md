# 期货信号系统 · 操作说明（v23 七品种定稿）

> 一句话：**先看路况，再看信号；震荡不碰，趋势顺势，出场永远比赛进场优先。**
> 全部结论来自 2017-01 ~ 2026-11 日线回测（7 品种共 162 笔），口径见文末「数据口径」。

---

## 0. 一页速览

| 问题 | 答案 |
|---|---|
| 什么时候能开仓 | 只在**趋势**或**过渡态**，且出现该品种允许的那几种信号 |
| 什么时候必须空仓 | **震荡**（振幅<10% + MA34 走平 + 穿梭≥3 次）——**一律不开仓、不推信号** |
| 什么时候必须出 | ①失效/强烈离场 → ②破 MA26 或吊灯 3ATR → ③30% 本金熔断（盘中强平） |
| 什么时候能反手 | 原仓**已经平掉**之后，才允许按反向信号开新仓 |
| 看哪里 | 网页价格行右侧的「当前路况」横条 = 第一眼（v26 起全页只此一块；点右上「ⓘ 路况判据」展开布林带宽 / MA60 证据）；下面「策略持仓看板」= 定稿方案持仓与生效口径，「进场雷达」= 方向参考，「出场雷达」= 独立顶底 + 持仓防守线；「信号栏 · 消息归档」= 微信口径的当日消息流（v26.2 起图上的▮方块 / 黄◆ / 青◇ / 白箭头都能点开看明细，顶部「ⓘ 图上标记对照」写明哪类去哪查） |
| 一天看几次 | **15:20**（正式、唯一入账）+ **15:50**（兜底重试）+ **11:33**（盘中预警、不入账）+ **23:10**（夜盘预警、不入账，绝不改 K 线 / state） |

## 1. 这套系统在赌什么

它不是「猜涨跌」，是**在少数真正走出趋势的行情里，用很小的止损去博很大的盈利**：

- 七个品种**胜率全部低于 70%**，其中四个在 28%~50%；
- 但盈亏比（平均盈利 ÷ 平均亏损）在 **1.36 ~ 12.25**；
- 所以：**胜率低是设计特征，不是故障**。按单笔胜率去评判它，一定会判断错。

一句话记住：**允许自己频繁小亏，只为了那 1 笔吃满的。**

## 2. 资金与仓位（模块一）

| 项目 | 规则 |
|---|---|
| 初始本金 | 10,000 元 |
| 每次仓位 | **固定 1 手**，不加仓、不金字塔、不摊平 |
| 保证金不足 | 自动追加 10,000 元并记录次数；实测七品种近 10 年 **0 次追加** |
| 熔断线 | 单笔浮亏 ≥ 3,000 元（本金 30%）→ **盘中按触发价强平**，不等收盘 |
| 结算 | 手续费双边计入（按手 / 按千分比，见各品种参数） |

> 熔断是「唯一允许的盘中成交」。其余所有决策都是**收盘确认、次日开盘执行**，不猜盘中。

---

## 3. 路况三分法（这是整套系统的总开关）

只使用截至当日的数据，不用未来 K 线：

| 路况 | 判定（需同时成立） | 系统动作 |
|---|---|---|
| **上涨 / 下跌趋势** | 幅度 ≥12% **或** ≥3×ATR；持续 ≥15 个交易日；MA34 明显倾斜 | 按该品种「趋势进场集合」顺势开仓 |
| **震荡** | 20 日窗口振幅 <10%；MA34 走平（位移 <窗口振幅 50%）；价格穿梭 MA34 ≥3 次 | **观望空仓 + 推送静默** |
| **过渡态** | 以上两类都不满足 | 只允许「顶底雷达 / 进场预警 / WM结构」（按品种） |

十年样本里，趋势天占 42%、震荡 10%、**过渡 48%**——过渡态占近一半，所以它不是边角料，是主战场之一。

## 4. 什么情况进（进场集合，按品种）

所有品种的底层规则相同，只有「用哪几种信号」不同：

**六种进场信号**

| 代码 | 名称 | 含义 |
|---|---|---|
| `pred` | 顶底雷达 | 顶/底四条证据齐备且 ADX 过门槛（反转） |
| `warn` | 进场预警 | 三条胜出（或四条但 ADX 未过门槛），比雷达早一步 |
| `mw` | W/M 结构 | 双顶/双底 + **颈线突破确认**（反转） |
| `tf` | 转折确认 | 自极值回撤 ≥3.5ATR → 顺新方向（趋势跟踪） |
| `confirm` | 反转兑现 | 雷达的预测被价格穿越 MA **兑现**了 → 顺新方向（确认，不是预测） |
| — | 强烈离场 / 失效 | 只用于出场，不用于进场 |

**七品种各自允许什么**

| 品种 | 方案 | 趋势中可进 | 过渡态可进 | 震荡 |
|---|---|---|---|---|
| 甲醇 MA | G1 | WM结构 + 反转兑现 | 顶底雷达 | — |
| 玻璃 FG | G1 | WM结构 + 反转兑现 | 顶底雷达 | — |
| 豆粕 M | G1 | WM结构 + 反转兑现 | 顶底雷达 | — |
| 豆油 Y | G2 | 转折确认 + 反转兑现 | 顶底雷达 | — |
| 棕榈油 P | G2 | 转折确认 + 反转兑现 | 顶底雷达 | — |
| 热卷 HC | G8 | WM结构 + 反转兑现 | 顶底雷达 + WM结构 | — |
| 锰硅 SM | G4 | WM结构 + 反转兑现 | 顶底雷达 + 进场预警 | — |

**三条硬约束（七品种全都开着）**

1. **只顺势**：上涨趋势只做多、下跌趋势只做空。逆势信号直接丢弃，不占名额。
2. **震荡零开仓**：`震荡 → 进场集合为空`，代码层面就没有开仓分支。
3. **同一天多信号只取一条**：优先级 顶底雷达 > 进场预警 > WM结构 > 转折确认 > 反转兑现；方向冲突时以优先高者为准。

**成交时点**：T 日收盘出信号 → **T+1 开盘价**成交。永远不追当天的收盘价。

## 5. 什么情况出（三档优先级，这套系统最核心的部分）

同一个决策点（T 日收盘）按顺序裁决，命中就停，不再往下看：

### 第一档 · 防守（保命）
- **失效（白圈）**：当初建仓那条信号的失效条件出现。严格配对——只对「建仓这条信号」有效，别的信号的失效不算。
  四条触发条件（v24 起）：
  1. **反向幅度**：自信号日收盘逆行 >1.5 ATR（20 根内）；
  2. **均线破位**：先在内侧、再**连续 2 根**收盘跌破 MA26/MA34 且超出 **0.5 ATR**；
     **单根就暴破 ≥0.8 ATR → 立即算，不等确认**（保命快通道，防真崩）；
  3. **时间衰竭**：5 根内没创新高/低，反而收破信号日低点/高点；
  4. **原版止损**：MA26 反向穿越（同第 2 条口径）或吊灯 3ATR 触发。
- **强烈离场雷达**（level = strong）：独立出场评估，趋势中也照平（`xsig_trend=true`，不把它交给均线去拖）。

> v24 的关键：**一根小阴线不再算破线**。要连 2 根收在均线外 0.5 ATR 才算；但一根就砸穿 0.8 ATR 的，当天就认，不等。10 年实测：胜率 46.9%→50.0%、盈亏比 3.30→3.38、回撤 37.4%→35.8%（净收益 +13,003 元）。

### 第二档 · 底线（控制单笔亏损）
- **破 MA26**：多头收盘 < MA26 − 0.5 ATR / 空头收盘 > MA26 + 0.5 ATR，且连续 2 根；单根暴破 ≥0.8 ATR 立即走；
- **吊灯 3ATR**：多头从「建仓后最高价」回撤 ≥3×ATR；空头从「建仓后最低价」反弹 ≥3×ATR。

### 第三档 · 熔断（本金安全线，盘中执行）
- 浮亏 ≥3,000 元 → 按触发价**当场平仓**，这是唯一不等收盘的动作。

### 出场之后
- 只有**原仓已经平掉**，才允许按反向进场信号开新仓（= 反手）。原仓没平就出反向信号 → 记一条「忽略」，不动。

> 为什么这样排：如果先看反手，就会出现「为了反手而平仓」，等于让新信号决定旧仓的去留——这正是之前回测虚高的根源。

## 8. 每天怎么用（3 分钟流程)

1. **打开页面，先看价格行右侧的「当前路况」横条**（紧挨涨跌幅，两行：上行路况/策略+验证，下行允许清单）——这是第一眼，其他都靠后。要看判据数值，点右上「ⓘ 路况判据」展开两行（默认收起，不占高度）。
2. **震荡** → 关掉，什么都不做。这是纪律，不是遗漏。
3. **有持仓** → 看「策略持仓看板」里的「下一次触发条件」与「当前生效口径」（白圈 v24 / 基础出场 / 熔断 / 6 通道 / **v27 极值禁令**）；吊灯、MA26 的具体离场线数值看「出场雷达 · 持仓防守线」。
4. **空仓 + 趋势/过渡** → 看有没有出现该品种允许的信号（看板会写清等哪种）。进场雷达只给方向参考，不是建仓指令。
5. **收到微信推送** → 按 6 条通道执行；推送里一定带【当前路况】，路况不对就别动手。
6. **看到图上有图标想查** → 先悬停（手机长按）看文字提示，再点开看明细：▮方块是方案回测该笔、黄◆是离场原因、青◇/白箭头是离场复盘。列表里对应的消息在「信号栏」，顶部「ⓘ 图上标记对照」写清了哪类在图上点、哪类在列表看。**带 `[研究参考·非建仓指令]` 的行只读，别动手。**

**两班数据**

| 班次 | 时间 | 作用 | 是否入账 |
|---|---|---|---|
| 正式 | 15:20 | 生成当天全部结论、信号记录、页面数据 | **是，唯一口径** |
| 盘中预警 | 11:33 | 用今日到此刻的临时 K 线提前跑一遍，只报「出场 / 进场 / 持仓中路况翻转 / 空仓转趋势」 | 否，卡片固定标「非收盘确认」 |

11:33 那班的兑现率：盘中翻转 MA34 状态后收盘兑现 90.9%（33 次中 30 次），MA26 一致率 97.1%，吊灯 98.8%。所以它是**预期**，可以用它提前安排资金和挂单，但**不能当结论**。

**六条推送通道（v25 定稿）**

旧的「趋势确认（tf）」推送通道已于 2026-11-10 彻底关停。现在微信只有这 6 条，按优先级：

| # | 通道 | 触发条件 | 性质 | 震荡市推不推 |
|---|---|---|---|---|
| ① | 🛑 失效打叉 | 原信号被证伪（与 K 线白圈同源，v24 口径） | 出场 | **推** |
| ② | 🔥 方案内信号 | 该品种定稿方案的进场集合 + 路况允许 + 顺势 | 进场（唯一算「指令」） | 不推 |
| ③ | 🔔 反转预警 | 概率 ≥70%，不在方案内的强制标注「仅作方向参考」 | 进场（参考） | 不推 |
| ④ | ⚠ 出场预警 | 盘整特征点亮，给出吊灯 / MA26 离场线具体数值 | 出场 | **推** |
| ⑤ | 🔔 独立出场雷达 ＋ 🏔 大结构 | 顶部/底部出场雷达（强=建议离场 · 弱=建议减仓）；另加**大级别结构双顶/底**信息推送（两峰间隔 ≥20 根且颈线深度 ≥3.5 ATR，小结构不推） | 出场 / 结构信息 | **推** |
| ⑥ | 🚨 30% 熔断 | 单笔浮亏 ≥ 30% 本金（约 3000 元） | 出场（强制） | **推** |

规则一句话：**进场看路况，出场不看路况**。震荡里系统对你闭嘴，但你手上的单子一旦破线、熔断、或出场雷达亮灯，照样推——震荡里把出场也静音，等于自断退路。

> **v26.2 补**：🏔 大结构仍是第 ⑤ 条通道内的一种事件，**没有新增第 7 条通道**，
> 与顶底预警同一条微信消息一起发。它是**结构信息，不是交易指令**：卡片与信号栏归档行都强制带
> `[研究参考·非建仓指令]`，运行时还会硬扫描「进场 / 开仓 / 建仓 / 做多 / 做空 / 反手」等字眼，
> 命中就拦下不发。微信推过的 `mw` / `tf` 形态在信号栏都能查到对应只读记录。
> 卡片标题已改为「信号栏 · 消息归档」，切到周 / 月线时会亮 `⚠️ 当前为日线归档口径`。

**🛡 v27 交易铁律【顶不做多 · 底不做空】**

信号生成日回看 **60 根**日线，`LL=60日最低`、`HH=60日最高`、`C=当日收盘`：

- 做多：`(C/LL−1) ≥ 20%` **且** `(C−LL)/(HH−LL) ≥ 0.90` → 拦截
- 做空：`(1−C/HH) ≥ 20%` **且** `(C−LL)/(HH−LL) ≤ 0.10` → 拦截

命中即**取消该笔进场**：图上不画「进多 / 进空」方块、信号栏不留记录、微信不推。
被拦的是 `pred / warn / mw / confirm / tf` 五类进场信号；
**出场类一律不动**（白圈 / 吊灯 / MA26 / 30% 熔断 / 独立出场雷达照常推）。
6 条推送通道结构没变，没有新增或删减通道。

这不是前端隐藏，而是引擎层根本不接受这些信号，随后按新铁律重跑同一套方案账本——
所以「策略持仓看板逐笔清单 / 图上方块 / 信号栏」三者仍然同源，不会出现账本撕裂。
10 年回测：被拦 38 笔胜率 28.9%、盈亏比 0.91、净 R 为负；样本外近 3 年 8 笔全亏。
代价是账本净收益 −7.2%、回撤 45.8%→46.5%——**这是为纪律付的保险费，不是收益优化**。
完整数据表见 `reports/v27_极值偏离度回测.md`。

如果某个位置你觉得该有信号却没有，先展开信号栏顶部「ⓘ 图上标记对照」看「极值禁令」一行，
别以为是数据漏了。

## 9. 不要做的事

1. **不要看胜率下单。** 七品种四个低于 50%，SM 只有 28.9%；它们靠盈亏比赚钱。
2. **不要在震荡里"手痒"。** 震荡段回测是净亏，系统用「零开仓」把这段直接砍掉。
3. **不要扛单等反向信号。** 出场优先级里防守第一，均线第二，反手第三，顺序反了整套就崩。
4. **不要用 11:33 的价格改记录。** 盘中价不是收盘价，写进去会永久污染历史。
5. **不要因为一个月没推送就认为系统坏了。** 震荡静默是设计：回放 20 个交易日只有约 9 条预警，87% 的品种日应当静默。
6. **不要给单个品种加杠杆。** 1 手是刻意的小，为了让 30% 熔断有意义。

## 10. 已知局限（必须知道）

1. **55% 胜率门槛与 30% 熔断在数学上互斥**：232 条候选策略里，双段正收益且胜率 >55% 的只有 4 条，其中 2 条验证段只有 1 笔。所以定稿口径改成「双段净>0 + 盈亏比≥1.2 + 回撤≤40% + 验证≥3 笔」，**这是主动偏离，不是没做到**。
2. **豆油 Y 验证段只有 3 笔**，样本薄；**玻璃 FG 近 1 年 0 笔**，等于近一年没干活。
3. **单笔最大亏损可能超过 3,000 元**：跳空穿透时成交价会滑过熔断价，实测最深 −3,412 元（8/3,529 笔超 −3,100）。
4. **年化数据基于 1 手固定仓位**，不代表加仓后的收益，也不代表可以复制到别的品种。
5. 回测含手续费、按 T+1 开盘成交；**未含**滑点、涨跌停无法成交、保证金比例调整。

## 11. 数据没更新怎么办（v27.1 自愈机制）

**先看哪里**：线上 `data/index.json` 的 `built`，以及 7 个品种 K 线的末根日期。代码是新的、K 线是旧的不算系统坏了，只是班次没跑。

**系统会自动做三件事，一般不用你管**：

1. **取数重试（班次内）**：15:20 / 15:50 正式班次先做只读预检，7 个品种当日日线没取齐就等 4 分钟重取，最多 5 轮。取齐后整条写盘流程只跑一次 —— 不把 `daily.py` / `data_build.py` 放进重试循环，是为了不重复写 `state.json`、不重复推微信。
2. **产物校验（班次内）**：渲染完再核对 7 品种末根一致、`data/` 与 `dist/data/` 一致、页面与数据包一致、策略口径齐全、`built` 是当天；不通过就阻断提交，宁可不更新也不推残缺数据。
3. **班次补跑（班次外）**：如果 GitHub 整个定时任务没触发（国内网络与平台延迟都可能），15:55 / 16:20 / 16:45 / 17:10 / 17:40 / 18:10 / 18:40 有 7 个只读巡检，发现 `built` 没刷新或品种不齐就自动派发一次正式班次；已有任务在跑或刚跑完 12 分钟内会跳过，不会重复触发。

**边界（很重要）**：

- **20:00 之后只走「late 静默补跑」（v28 起）**。21:53 / 22:53 两个尾单班次允许写盘，但安全性不再靠时间闸门，而是靠 `build.asof_day()`：所有日线、分钟线在离开 `build.py` 之前，日期晚于「最后一个已收盘交易日」的行会被物理剔除 —— 夜盘那半截 bar（属于下一交易日）根本进不来。这两个班次的微信推送被强制静音，只静默更新页面。**23:00 之后仍然一律拒绝**。
- 补跑走的仍是同一套 `daily.yml` 正式流程，K 线永远只按 15:20 / 15:50 两班算，**没有新增第三个写盘班次**。
- 当天休市或数据源确实没出新 bar 时，预检 5 轮后会打 warning 放行、复用旧数据，不会造出假 K 线。
- **20:00 之后不要手动点 `daily.yml` 的 Run workflow**（不带 force）—— 会被夜盘闸门 `exit 3` 拒绝。要补数就等次日 15:25，或者让它走 21:53 的晚班尾单。

**想自己查**：`python ci_audit.py`（本地 vs GitHub 逐文件一致 + CI 依赖闭包 + 7 品种策略口径全盘联动）；`python fresh_guard.py --verify`（产物一致性）。

> 2026-11-10 的实例：当天 `daily-scan` 零次运行，但真实联网探测 7/7 品种都已可取 11-10 完整日线 —— 缺的只是「班次跑一次」，不是数据本身。

## 12. 外部定时器（cron-job.org）—— 这才是实盘真正依赖的那条路

### 12.1 为什么必须上它

GitHub 原生 schedule 是 best-effort。官方文档明说高负载会延迟、低活跃仓库的班次会被丢弃。本仓库的实测账：

| 日期 | 应该跑 | 实际跑 | 实际落地时间（北京） |
|---|---|---|---|
| 11-04 ~ 11-10 | 每天 9 班 | **每天只有 2 班** | 23:04 ~ 次日 01:50 |
| 11-11（改 cron 前） | 9 班 | **0 班** | 全天没来 |

延迟实测 **+7.6 ~ 9.6 小时**，丢弃率约 **80%**。这个数字对实盘不可接受，所以改成「外部定时器精确打 `repository_dispatch`」——这条路不进 GitHub 的调度队列，触发率接近 100%，而且**跟你的电脑、手机是否开机完全无关**。

### 12.2 一天三个时段 · 6 个任务的对账关系

先说结论：**一天只有一次写盘（15:25，15:50 是同一件事的补跑），另外两班严格只读。**

| 时段 | 北京时间 | 写不写盘 | 干什么 | 推送 |
|---|---|---|---|---|
| ① 盘中预警 | **11:33** | **只读**（`contents: read`） | 午盘收盘后拼一根临时日线，提前算「会不会多出一笔进出」 | 只在真会多出一笔时推 |
| ② 正式入库 | **15:25 / 15:50** | **唯一写盘**（`contents: write`） | 写 `data/` + 重算信号 + 重渲 K 线页 + 推微信 | 推 |
| ③ 夜盘预警 | **23:10** | **只读**（`contents: read`） | 用夜盘 bar 推演「明早开盘就是这个价会不会出事」 | 命中才推 |

两个只读班次的只读属性不是靠自觉，是三层硬约束：

1. workflow 里 `permissions: contents: read` —— 就算脚本写错也 push 不上去；
2. 每个只读班最后一步都有 `git status --porcelain` 断言，**只要有任何文件改动，本次运行直接判失败**；
3. 脚本本身不碰 `state.json` / `data/` / `dist/`。

对应到 cron-job.org 的 6 个任务（全部周一至周五，时区 `Asia/Shanghai`，不换算 UTC）：

| 任务名 | 北京时间 | 事件名 | 任务 ID | 属哪个时段 | 作用 |
|---|---|---|---|---|---|
| 盘中预警 11:33 | **11:33** | `intraday-warn` | `8842682` | ① 只读 | 提前知道今天要不要挂单 |
| 日盘入库 15:25 | **15:25** | `daily-scan` | `8842618` | ② 写盘 | 主班次。收盘后数据源一般 15:10–15:20 放出日线 |
| 日盘入库 15:50 | **15:50** | `daily-scan` | `8842619` | ② 写盘 | 补班次。主班次遇延迟时补上（已写过则幂等跳过） |
| 数据看门狗 16:40 | **16:40** | `data-watchdog` | `8842620` | ② 看护 | 核对线上 7 品种是否已是当日日线，没到位就自己补跑 |
| 晚班尾单 21:53 | **21:53** | `daily-scan` | `8842621` | ② 写盘 | 极少数数据源当晚才补发时才会写；**微信强制静音** |
| 夜盘预警 23:10 | **23:10** | `night-warn` | `8842683` | ③ 只读 | 明早开盘的风险预演 |

**已于 2026-11-11 23:15 / 23:33 两次建成并实测**，服务端读回的配置与上表逐项一致（`enabled=true`、`requestMethod=1`(POST)、`timezone=Asia/Shanghai`、`wdays=[1,2,3,4,5]`、`expiresAt=0`(永不结束)）。

首班执行时间：

```
2026-11-12 11:33  盘中预警（只读）      ← 明天上午第一班
2026-11-12 15:25  正式入库（写盘）
2026-11-12 15:50  正式入库（补）
2026-11-12 16:40  数据看门狗
2026-11-12 21:53  晚班尾单（静默）
2026-11-12 23:10  夜盘预警（只读）
```

连通性验证用的「无副作用」打法：临时建一个任务发 `{"event_type":"ping-probe-noop"}`（这个事件名没有任何 workflow 监听，GitHub 照样返回 204 但不会启动任何运行），跑完即删。

```
北京时间 2026-11-11 23:16:08   status=1 (No Content)   HTTP 204   duration 1536ms
```

204 等于「鉴权通过 + 请求体被接受」，链路确认可用。同时核对过 GitHub Actions：这一发**没有**产生任何多余 run。

另外对只读班做过一次**真实派发**验证（`intraday-warn`，run #4 / #5，`event=repository_dispatch`，两次均 6 步全绿），并核对日志确认只读断言通过、且用的是北京时间：

```
当前北京时间 2026-11-11 23:26 不在日盘时段（09:00-15:00），盘中预警不执行。
```

（runner 内部此刻是 UTC 15:26 —— 日志显示的是北京时间，正是下面 12.9 那个 bug 修好后的结果。）

失败通知已开启（`onFailure` / `onDisable` / `onSslCertExpiry` 全开），连不上或 401 会发邮件到你 cron-job.org 注册邮箱。

请求细节（想手工核对时看）：

```
POST https://api.github.com/repos/dongzij/futures-signal-desk/dispatches
Authorization: Bearer <你的 PAT>
Accept: application/vnd.github+json
X-GitHub-Api-Version: 2022-11-28
Content-Type: application/json

{"event_type":"daily-scan"}      # 或 data-watchdog
```

### 12.3 平常怎么确认它在跑

**看 cron-job.org**：登录后首页就是任务列表，每行显示最近一次执行的状态码、耗时、下次执行时间。点任务名进去有「History」页，能看到每次请求的 HTTP 状态和**响应体**（已开 `saveResponses`）：
- `204` = 成功（GitHub 的 dispatch 接口成功就是 204 空响应）
- `401` = PAT 失效或被吊销 → 换 PAT 后改任务 Header
- `404` = 仓库名写错，或 PAT 没有这个仓库的权限

**看 GitHub 侧是否真的起来了**：Actions 里 `daily-scan` 的行，`event` 那一列显示 **`repository_dispatch`** 就说明是外部定时器打进来的（`schedule` 是 GitHub 自己触发的、`workflow_dispatch` 是你手点的）。外部触发的班次从请求到开始跑一般 **10–20 秒**。

**看数据到底有没有更新**：`data/index.json` 的 `built` 是不是当天，7 品种末根是不是当天。

### 12.4 出问题先看这三个地方

1. **cron-job.org 显示执行了但 GitHub 没 run** → 九成是 PAT 过期/被吊销。GitHub 的 PAT 有有效期，到期必须换。
2. **cron-job.org 显示 403 且响应体是 `Resource not accessible`** → PAT 权限不够。`repository_dispatch` 需要 **Contents 写权限**（classic PAT 是勾 `repo`）。
3. **GitHub 起来了但 guard 判定跳过** → 这是正常行为：数据源当天还没放出日线，或当天已经写过（幂等）。不是故障，不用管。

### 12.5 一个容易被忽略的坑

cron-job.org 免费账号**长期不登录会暂停任务**。它会在暂停前发邮件提醒，收到邮件登录一下就行。建议顺手把这个邮箱的提醒开着——这比发现"数据三天没更新"再回头查要省事得多。

### 12.6 换 PAT 怎么做（PAT 到期 / 被吊销时）

症状：cron-job.org 里任务显示 `401`，GitHub 里一条 run 都没有，邮件开始告警。

不要进网页一个个手改。本地一条命令，四个任务的 Header 一起换成新 PAT：

```bash
cd deploy
CRONJOB_API_KEY=<cron-job API key> GH_PAT=<新 PAT> python cron_setup.py --apply
```

**直接跑就行，不用先删。** `--apply` 对已存在的同名任务会走 `PATCH` 把全量配置（URL / Header / body / 时间 / 通知）重新校准一遍，换 PAT、改时间、补开通知都是这一条命令的事，不会重复建任务。

跑完会自动打印一段「配置自检（服务端回读）」，四项全 `✓` 才算真的改对了：

```
──────── 配置自检（服务端回读） ────────
  ✓ 期货信号·日盘入库 15:25                  下次=11-12 15:25 Thu
  ✓ 期货信号·日盘入库 15:50                  下次=11-12 15:50 Thu
  ✓ 期货信号·数据看门狗 16:40                 下次=11-12 16:40 Thu
  ✓ 期货信号·晚班尾单 21:53（静默）              下次=11-12 21:53 Thu
──────── 全部通过 ────────
```

> 这个自检不是装饰。通知字段曾经写成复数 `notifications`，服务端**不报错、直接丢掉**，表现是「创建成功但失败永远不发邮件」。所以只信回读，不信创建返回值。

### 12.7 不登网页，用命令行核对（推荐）

```bash
cd deploy
CRONJOB_API_KEY=xxx python cron_setup.py --list      # 任务清单 + 下次执行时间 + 上次状态码
```

想看某一次的真实响应（比如确认到底是 204 还是 401），查历史接口：

```bash
# 把 <jobId> 换成 8842618 等；看 statusText / httpStatus / date
curl -s -H "Authorization: Bearer $CRONJOB_API_KEY" https://api.cron-job.org/jobs/8842618/history
```

`statusText` 会是 `No Content`(204，正常) / `Unauthorized`(401，PAT 挂了) / `Not Found`(404，仓库名错)。

### 12.8 建任务时踩过的两个 API 坑（改脚本的人必看）

1. **新建任务必须 `PUT /jobs`**，`POST` 返回的是 **404 而不是 405**。`cron_setup.py` 最初靠「405 才回退到 PUT」判断，结果 404 直接把脚本打断。现在固定用 PUT。
2. **通知字段是单数 `notification`**，写成 `notifications` 会被**静默忽略**（不报错，但通知全关）。所以建完一定要回读 `jobDetails.notification.onFailure` 确认是 `true`，别只看创建成功。

### 12.9 v28.4 修掉的时区 bug（11:33 这班其实一直在空转）

**症状**：外部定时器接好之后才发现，11:33 那班就算准时跑也什么都不做。

**根因**：`intraday_warn.py` 用裸 `datetime.now()` 判「是否在 9:00–15:00 日盘时段」，而 GitHub runner 的本地时区是 **UTC**。北京 11:33 在容器里是 `03:33`，`9 <= 3` 为假 → 直接 `return`，一行计算都不做。

**为什么一直没被发现**：这班的 cron 是 `33 3`（UTC），实测延迟 6–10 小时后，真实触发落在北京 **19:22 / 19:37**（UTC 11:22 / 11:37），**恰好落进 UTC 的 9–15 区间**，所以 Actions 显示 success、没有任何报错。但它算的是「晚上拿全天数据拼出来的临时日线」，口径完全不对。历史那几次「成功」全是这个假象。

**修法**：统一用 `nightgate.bj_now()`（北京 naive 时间），并打印时区上下文方便以后排错。修复后 CI 日志实测：

```
当前北京时间 2026-11-11 23:26 不在日盘时段（09:00-15:00），盘中预警不执行。
```

runner 内部此刻是 UTC `15:26`，日志显示 `23:26` —— 北京时间生效。

**给以后改代码的人的规矩**：所有脚本里**禁止裸用 `datetime.now()` 判断时段/日期**，一律 `nightgate.bj_now()` 或 `fresh_guard.bj_now()`。GitHub runner 是 UTC，本地是北京，这个坑会反复出现。

## 13. 微信推送的时段规则（v28.2 起晚班静音）

推送只在一个窗口里发：**北京时间 15:00–20:00**。规则落在 `daily.py` 的 `post_push()` 一个点上，六个调用点全部经过它：

| 情况 | 是否推送 | 原因 |
|---|---|---|
| 15:25 / 15:50 正式班次 | ✅ 推 | 正常日盘时段 |
| 15:55–18:40 巡检补跑出来的班次 | ✅ 推 | 仍在这个窗口内 |
| **21:53 / 22:53 晚班（late）** | ❌ **静音** | 你已休息；补跑只需页面静默更新 |
| 深夜被 GitHub 延迟到的班次 | ❌ 静音 | 不在 15:00–20:00 |
| 11:33 盘中预警 | ✅ 推 | 单独绕过时段闸门（`gated=False`） |
| 23:10 夜盘预警（`night.yml`） | ✅ 推 | 走自己的 `push()`，不经过这个闸门 |

静音的两种触发方式是**双保险**：代码里认 `RUN_MODE=late`，workflow 里再写死 `NO_PUSH=1`。任一改动失效，另一条仍然拦得住。

静音时日志会打印 `[push] 静音（原因）：本条不推送 —— 标题`，班次末尾汇总 `push muted N 条`。**静音不等于失败**：这条消息被视为「已处理」，不会让第二天把昨天的旧信号当成新信号补推一遍。
