# v27.2 · 定时任务修复与准点更新方案（2026-11-11）

## 一、问题回顾（实测数据，非猜测）

GitHub Actions `schedule` 在本仓库**所有** workflow 上都系统性晚点 6~10 小时：

| Workflow | cron（UTC） | 应触发（北京） | 实际触发（UTC） | 实际（北京） | 延迟 |
|---|---|---|---|---|---|
| daily-scan | `20 7` / `50 7` | 15:20 / 15:50 | 15:37 / 15:50 | 23:37 / 23:50 | ~8h |
| intraday-warn | `33 3` | 11:33 | 11:37 | 19:37 | ~8h |
| night-warn | `10 15` | 23:10 | 21:15 | 次日 05:15 | ~6h |
| data-watchdog | `55 7` ~ `40 10` | 15:55~18:40 | 全部晚点 | 深夜 | ~8h |

11-10 的 daily-scan #23/#24 因此落在北京时间 23:37/23:50，被 v27.1 新增的
`fresh_guard.py` 时间闸门以 **exit code 3** 拒绝（注解经 API 核实），job 标红并每天发失败邮件。
这其实是守卫**按设计工作**：20:00 后绝不能写盘，否则夜盘半截 bar 会永久污染日线与账本。

11-11 上午有人把 `precheck()` 里的 `return 3` 改成 `return 0`（提交 38fa48d），
daily-scan #26 随即"成功"。但这是**更危险的回归**：

- 10:36（非 15:00-20:00 窗口）触发的班次跳过了整个新鲜度预检；
- 流水线照常写 `state.json`、重建 `dist/data`、渲染页面并 push；
- 结果 `index.built = 2026-11-11 10:43`，但 7 品种末根仍是 `2026-11-10`
  → **页面显示"今天已更新"，实际是昨天的数据**（假新鲜）。

`tools/dispatch_daily.py --check` 可直接复现该状态。

## 三、如何做到"每天按时更新"

GitHub 官方说明 schedule 在高负载时会排队、延迟甚至漏跑，**无法保证准点**。
因此正式班次改由**外部精确触发器**即时派发（workflow_dispatch / repository_dispatch 不排队）。

### 步骤 1：创建 PAT（一次性）

GitHub → Settings → Developer settings → Personal access tokens：

- 经典 PAT：勾选 `repo`；
- 或细粒度 PAT：仅授权 `dongzij/futures-signal-desk`，权限 `Actions: read and write` + `Contents: read`。

把 token 放进环境变量 `GH_TOKEN`，或写入 `~/.config/futures-signal-desk/github_pat`。
**不要写进仓库、不要提交**。

### 步骤 2：配置外部定时器（任选其一）

| 时间点（北京） | 命令 |
|---|---|
| 周一~周五 15:20 | `python tools/dispatch_daily.py --workflow daily` |
| 周一~周五 15:50 | `python tools/dispatch_daily.py --workflow daily`（幂等，已更新会自动跳过） |
| 周一~周五 11:33 | `python tools/dispatch_daily.py --workflow intraday` |
| 周一~周五 23:10 | `python tools/dispatch_daily.py --workflow night` |
| 15:55~18:40 巡检 | `python tools/dispatch_daily.py --workflow watchdog` |

载体建议（任选）：

1. **cron-job.org**：免费、支持自定义 Header，直接请求
   `POST https://api.github.com/repos/dongzij/futures-signal-desk/actions/workflows/daily.yml/dispatches`，
   Header `Authorization: Bearer <PAT>`、`Accept: application/vnd.github+json`，
   Body `{"ref":"main","inputs":{"force":"0"}}`，按 UTC 07:20 / 07:50 配置。
2. **腾讯云函数 SCF / 阿里云函数**：定时触发 + 环境变量放 PAT，直接跑本脚本。
3. **本机计划任务**（Windows 任务计划 / crontab）：把 `tools/dispatch_daily.py` 挂上即可，
   要求该机器在 15:20 开机。WorkBuddy 的定时自动化也走这条路。
4. **GitHub schedule + 延迟补偿 cron**：保留作兜底，不依赖任何外部服务；
   若某天延迟恰好落在 15:00-20:00 窗口，闸门会自动放行并补上数据。

### 步骤 3：验证

```bash
python tools/dispatch_daily.py --check                 # 只读体检，无需 token
python tools/dispatch_daily.py --workflow daily --wait  # 准点触发并等待结果
```

体检输出中「当日数据已到位 = True」且 `built` 为当天 15:20 之后，才算真正更新成功。

## 四、纪律边界（未改动）

- 北京时间 20:00 - 次日 08:00 是夜盘窗口，`nightgate.py` 仍强制拒绝所有写盘入口；
- `force=1` 只跳过时间窗口预检，**不会**绕过 nightgate；
- 只读班次（intraday-warn / night-warn）与 watchdog 依旧不写任何数据文件；
- 微信推送仍由 `daily.py` 统一负责，不重复发。
