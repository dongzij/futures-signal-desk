# v28.2 · 外部定时器接入 + 晚班推送静音

日期：2026-11-11 晚
背景：v28.1 摸底发现 GitHub 原生 schedule 在本仓库的丢弃率约 80%，实盘不可接受；
用户同时要求晚班补跑一律静音，不允许半夜收到微信。

---

## 一、为什么必须上外部定时器（把账算清楚）

GitHub 官方对 `schedule` 的说明是 best-effort：高负载时排队、低活跃仓库的班次会被丢弃。
本仓库的实测记录：

| 区间 | 应跑班次 | 实跑班次 | 实际落地（北京时间） |
|---|---|---|---|
| 11-04 ~ 11-10 | 每天 9 班 | **每天 2 班** | 23:04 ~ 次日 01:50 |
| 11-11（改 cron 前） | 9 班 | **0 班** | 全天未触发 |

延迟实测 +7.6 ~ 9.6 小时。即使把 cron 错峰（v28.1 已做：`23 0,2,4` / `41 1,3,5` / `53 13,14`），
也只能提高命中率，**不可能保证 100%**。

结论：要满足「电脑手机关机也必须更新」，唯一可靠路径是外部定时器直接打
`repository_dispatch`，绕开 GitHub 的调度队列。

## 二、代码侧做了什么

### 2.1 新增 `cron_setup.py`

一条命令建好全部任务，幂等（同名已存在就跳过），并支持查看与清理：

```
python cron_setup.py --dry      # 只看清单，不发请求
python cron_setup.py --apply    # 创建（需 CRONJOB_API_KEY + GH_PAT）
python cron_setup.py --list     # 看现有任务、下次执行、上次状态
python cron_setup.py --remove   # 只删本脚本建的 4 个任务
```

任务定义（时区固定 `Asia/Shanghai`，不做 UTC 换算，避免时区误会）：

| 任务 | 北京时间 | 事件 | 作用 |
|---|---|---|---|
| 日盘入库 15:25 | 15:25 | `daily-scan` | 主班次 |
| 日盘入库 15:50 | 15:50 | `daily-scan` | 补班次（幂等，已写过就跳过） |
| 数据看门狗 16:40 | 16:40 | `data-watchdog` | 核对线上末根，没到位就补跑 |
| 晚班尾单 21:53 | 21:53 | `daily-scan` | 数据源当晚才补发时兜底，**静音** |

请求体与 cron-job.org 将发出的完全一致，已实测：

```
POST https://api.github.com/repos/dongzij/futures-signal-desk/dispatches
{"event_type":"daily-scan"}
→ 204 No Content
→ Actions 中出现 run#30，event=repository_dispatch，12 秒内起来
```

### 2.2 推送时段闸门（`daily.py`）

所有日盘微信推送都走 `post_push()`，闸门只加在这一处，六个调用点无需改动。

```python
def push_muted():
    if NO_PUSH:                       return "NO_PUSH=1"
    if RUN_MODE == "late":            return "RUN_MODE=late（晚班补跑）"
    if 北京时刻 not in [15:00,20:00):  return "不在日盘时段"
    return ""                          # 允许推送
```

三个关键设计取舍：

1. **静音返回 True 而不是 False**。返回 False 会让调用方认为推送失败、不消费
   「已推送」标记，第二天正常班次就会把昨天的旧信号当成新信号补推一遍 ——
   那反而是更大的打扰。静音的正确语义是「已处理，决定不发」。
2. **`intraday_warn.py` 显式 `gated=False`**。盘中预警跑在 11:33，天然在窗口外，
   不加这个参数会被统一规则误杀。
3. **`night_warn.py` 完全不动**。夜盘 23:10 的预警走自己的 `push()`，
   用户明确要这条通道，不能被这次改动波及。

### 2.3 workflow 双保险（`daily.yml`）

```yaml
NO_PUSH: ${{ steps.guard.outputs.run_mode == 'late' && '1' || '' }}
```

代码认 `RUN_MODE=late`，workflow 再写死 `NO_PUSH=1`。任一失效，另一条仍拦得住。

## 三、本地验证

推送闸门四种情况全部符合预期：

```
日盘 15:30 · RUN_MODE 空        -> 【允许推送】
日盘 15:30 · RUN_MODE=late     -> RUN_MODE=late（晚班补跑）
日盘 15:30 · NO_PUSH=1         -> NO_PUSH=1
真实 21:33 · RUN_MODE 空        -> 北京 21:33 不在 15:00-20:00 日盘时段
```

`post_push()` 实测日志：

```
[push] 静音（北京 21:33 不在 15:00-20:00 日盘时段）：本条不推送 —— 测试标题
返回值: True （已处理完毕，不重试）
```

## 四、待用户提供（这一步无法代劳）

外部定时器必须落到一个第三方账号上，两把钥匙：

| 变量 | 从哪拿 | 权限范围 |
|---|---|---|
| `GH_PAT` | GitHub → Settings → Developer settings → Tokens | classic：`repo` + `workflow`；fine-grained：Contents **Read and write** |
| `CRONJOB_API_KEY` | cron-job.org → 头像 → Settings → API | 免费账号即可生成 |

拿到后一条命令建完，脚本不会把 PAT 落盘、不会打印完整值（只打印头尾 7/4 位）。

## 五、出问题的三种典型症状

| 症状 | 原因 | 处理 |
|---|---|---|
| cron-job.org 执行了，GitHub 没 run | PAT 过期/被吊销 | 换 PAT，改任务 Header |
| 403 `Resource not accessible` | PAT 缺 Contents 写权限 | 补 `repo` 或 Contents RW |
| GitHub 起来了但 guard 跳过 | 数据源未放出，或当天已写过（幂等） | 正常行为，不用管 |

另：cron-job.org 免费账号**长期不登录会暂停任务**，暂停前会发邮件提醒，登录一次即可恢复。
